# 0.5.0 技术调查与实施边界

[English](TECHNICAL.md) · [计划](PLAN.zh-CN.md) · [验收](QA.zh-CN.md)

## 已核对的事实

2026-10-22只读比较正式0.4.2与保留的0.4.1应用：两者签名指定要求相同（相同应用标识和证书根），打包脚本使用稳定预览证书。没有读取凭据值或修改钥匙串。因此“每次换了证书”目前不能解释该现象；也不能据此宣称系统访问控制必然正常。仍是自签名、未公证预览。

`KeychainCredentialStore`使用传统通用密码项，后台读取禁止交互；`retryCredentialRead()`才允许显式系统确认。当前异常汇总为凭据读取失败；它不足以区分签名信任、锁定状态、旧项访问控制与其他拒绝原因。没有复现一次新的失败，也没有确认最终根因。

Apple说明系统用指定要求识别代码，Keychain与签名有关，但不同Keychain实现也有不同访问控制模型：[代码要求](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)、[macOS Keychain实现](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)。这些是调查依据，不是本机根因证明。

## 最小后续调查

先用独立测试service和无价值测试字符串做同证书／同路径旧新包读取、冷启动、锁屏恢复对照，记录错误码与指定要求匹配结果；只改测试项，不迁移生产凭据、不放宽信任。若隔离项通过而原项失败，再限定读取原项的非秘密访问属性并由系统完成必要授权。不得以删除旧凭据、改明文存储、全局放行或偷偷换登录方式消除提示。

原生界面区分“系统暂不允许读取”“未找到登录信息”“登录已失效”；只有实际响应支持时才显示具体原因。错误未知时保留中性说明。任何修复都必须用真实升级/重启复核，不以签名命令成功替代读取成功。

## 代码改动地图

- `QuotaReminderState`：新增可选节点集合，缺省四节点；合法值校验、去重／排序，不覆盖旧提醒历史。具体存储仍沿用现有提醒状态。
- `QuotaReminderEvaluator`／提醒store／模型：选择过滤和原有最临期合并规则一致；revision保护并发，accepted回执和账号归属不变。测试旧JSON、开关、重复开启、多个到期节点、失败重试、重启和未知账号恢复。
- `ResetExpiryReminderView`：开关下直接四个复选项，最少一个选择、禁用态及保存失败反馈。
- `QuotaPace.evaluate`：在现有过滤过程中产出可验证的连续时长、数量和中断原因；不另写第二套UI过滤算法。当前少于7个点会提前返回，不能直接拿`observedDuration`显示真实观察进度，需要补齐诊断证据。
- `DataStatusView`／既有pace说明：共享诊断，现有来源／错误／重试路径保留。连接已恢复而历史不足时不能诱导重新登录。

## 原型范围

无依赖HTML/CSS/JavaScript；全部数据为合成、只保存在页面内存。网络读取仅为加载自身静态文件。提供六种代表状态，未覆盖全部生产状态，原生状态清单见计划。没有生成系统通知、操作凭据或卡片；模拟保存失败不代表真实文件失败验收。

## 隔离复现更新

同路径／同证书的两个不同测试程序均通过严格签名核验，指定要求相同。测试旧程序创建和读取测试项均为0，新程序读取及冷读均为-25293；测试项删除为0。测试未读取生产凭据，也未改访问控制。完整根因仍待调查。[实施证据](implementation-evidence.json)不将此结果当作已修复。

显式单应用访问列表的独立对照也复现更新后-25293，测试项已删除；本机可用Developer ID签名身份数为0。未改变真实项或系统信任设置。

## 2026-10-23：分区匹配证据与处理边界

只读检查独立测试项的ACL描述，解码后得到`Partitions`仅含旧版本`cdhash`，新测试程序的内容哈希不在列表中。对现有ReadyCheck单一登录项也只请求引用和访问属性，不请求凭据数据：分区类型同样仅为`cdhash`，此前已获系统允许的稳定版和dev.1均在其中。没有修改任何真实项、系统信任或访问列表。

Apple公开的[Security分区识别实现](https://github.com/apple-oss-distributions/Security/blob/main/securityd/src/clientid.cpp#L260-L287)表明，可识别的Apple开发者签名使用团队分区，其他签名使用内容哈希。结合本机观察，这解释了“指定要求相同但内容变化仍需重新允许”的机制。它是基于源码和只读观测的判断；没有执行修改分区权限的因果对照，也不宣称已验证任何Developer ID新包。

当前自签名预览继续保留系统必要确认。未采用清空分区／加入所有应用／明文凭据／静默迁移等方式。后续若采用可识别的开发者团队签名，需要准备有效签名身份，并以真实升级验证改善；本机当前没有该身份，不能承诺已经解决升级确认。

另发现运行中的自动用卡账本受系统保护而读取失败。dev.2只修正显示：账本或凭据不可读取时显示“状态待确认”，不用灰色关闭开关表达未知；原授权文件及用卡执行逻辑不变。正常可读时保留原开关和确认流程。用户完成系统确认后，账本已恢复可读，原账号授权保留。同包冷启动自动读取成功，未再次要求确认。此前失败的集成用例及当前全量388项均通过；没有修改文件保护或授权，不能据此承诺未来不同二进制升级免确认。

## dev.3 用卡可靠性

- 已确认的兑换回执立即独立返回，不再被后续额度刷新断线覆盖；模型仍在成功后刷新额度。
- 授权账本在检查及原子替换后保留已打开的文件描述符；维持`completeUnlessOpen`保护与0600权限。路径指向的新文件必须重新打开核验，不能靠旧授权缓存继续执行；空白／损坏文件停止用卡。Apple说明了此[已打开文件保护类型](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeunlessopen)。此机制并不证明昨夜事件的确切原因。
- 请求准备前持久保存指定卡、稳定重试标识、开始时间／准备次数和待确认结果；用卡成功与通知分开。结果未确认时，在原卡到期前不能改用另一张卡。
- 持续保留分账号可用卡观察。卡片消失即使已到标称期限也保持未确认；只有明确服务端`consumed`／`expired`状态才能记录该事实。发起方未知的已用状态与ReadyCheck成功分开，不发送自动成功通知；明确回执离开列表后仍保留。
- 独立、有上限、0600的诊断文件只存原因、首次／最近检查、次数及异常提示提交状态，不含凭据和兑换授权，不能替代授权或发起请求。同一连续失败合并，系统接受一次异常提示后不反复弹出；提交失败可重试。
- 设置→提醒→自动用卡下展示与总览同源的记录。详情区分观察／提醒历史来源与已准备请求；旧到期提醒可显示缺失回执的历史卡片，但不能补造兑换结果。无账号归属的旧提醒不分配给当前账号。
- 重启未登录、退出、睡眠、凭据受限及存储不可访问仍可能阻止兑换。读取恢复及合成测试不能证明隔夜真实兑换；不为验收消耗真实卡。
