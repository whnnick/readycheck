通知图标阻塞项于10月10日在本机关闭：用户确认安装本地0.1.134后重启电脑，图标已恢复正确。此前16:56和23:44的测试只证明投递，不能证明实际图标。重启后结果来自用户验收，没有自动截图，也未隔离证明此前哪一步维护必不可少，不能将单独重启视为通用修复。签名、登录、权限和通知投递在重启前已验收。不宣称已删除或重绘系统历史通知。

验证命令：`scripts/check_release_consistency.sh`、`bash -n scripts/package_app.sh`、`swift test --build-system native --scratch-path <临时构建目录>`、既有DMG打包入口（隔离构建及产物目录）、DMG只读挂载检查及`codesign --verify --deep --strict`。原生构建后端避开Xcode构建目录扩展属性导致的签名失败，并保持打包所需的CLI可执行文件路径。

本机另进行一次性维护：最初重新登记已安装ReadyCheck、仅重启通知中心，用户截图证明不足以修复。随后发现Launch Services有32个ReadyCheck注册，其中包括0.1.89旧备份。取消旧ReadyCheck注册但保留文件，只保留现用安装应用的注册；旧备份移出应用程序目录并保留回滚。刷新当前用户的iconservicesagent、usernoted、usernotificationsd和通知中心进程。新测试提醒已投递，但系统日志记录横幅被屏幕共享状态抑制；用户检查通知中心，确认仍是旧仪表盘。系统级iconservicesd需要管理员验证，未能刷新。未清空通知数据库、权限或提醒历史。

补充渲染检查：通过公开NSWorkspace接口获取现用应用图标，实际栅格化为16、32、64、128、256像素；目视检查32、64、128像素均为C。这只能证明系统文件图标正确，不能代替通知渲染验收。旧版备份压缩包和哈希清单位于被忽略的本地构建目录，不进入发布产物。
