## P0-1：总览中的“接下来”摘要

需求N1：复用已经验证的账号、额度和卡片事实，展示最多两条与时间或处理动作有关的信息。

- 优先需要用户处理的明确异常，其次是最近的事件；正常时保持紧凑，不用大面积“可用”占位。相同优先级按事件时间排序，规则由同一状态模型提供。
- 首期聚焦5h自然重置与最早到期重置卡。时间来自官方读数；时间到了不等于额度已恢复，须新读数确认。7天信息继续完整保留在原处。
- 自动用卡已授权：说明卡片进入最后1小时后会尝试，仍需应用运行、凭据和新鲜读数有效。检查窗口起点不是保证执行时刻，不展示承诺性的执行倒计时。
- 自动用卡关闭：明确“自动使用未开启”，点击进入现有提醒设置；不暗中开启，不反复催促。
- 离线、旧缓存、卡片明细缺失或凭据异常：只说明尚不能确认及合适的“刷新／查看连接”入口，不沿用肯定的执行承诺。具体异常状态须有对应证据，不能把缺字段都说成断网。
- 总览可展示两条；菜单栏／Widget共享其中一条优先信息并链接同一详情，不维护不同口径。摘要与已有节奏区域合并去重，布局先评审，不再叠一张含义相近的大卡。
- Widget两行额度、最近1小时图、按钮与固定语义保留。若主显示为7天，图仍对应7天，新摘要明确标注5h，不偷换选择。刘海维持点击展开。

## P0-2：现有账户与权益中的重置卡详情

需求N2：从已有卡片到期明细打开详情，不新增主导航页。

- 显示最早到期者、当前账号授权范围、等待／确认中／已使用／暂无可重置窗口／需处理等可理解状态，以及下一步。
- 分别展示“用卡结果”与“通知状态”。例：服务端已确认用卡；成功通知未送达，通知待重试。只有真实请求进行中才写“正在重试”，不能把持久等待写成正在执行，也不能把通知失败写成用卡失败。
- 复用已有按账号、卡片、请求保存的执行记录和通知记录；提供对应通知记录入口，保留原通知历史入口。
- 旧记录只有最近更新时间和最终状态时，就展示已有证据；缺少的尝试次数、开始时间或阶段标为未记录，不补造完整过程时间线。字段扩展需向后兼容，不另建互相矛盾的账本。
- 不提供可能重新兑换另一张卡的泛化“重试”。未知结果沿用原卡、原请求标识及既有防重规则；“重试通知”不得再兑换。
- 设置页继续管理规则与授权，详情用于解释结果；现有自动用卡、到期提醒、低额及恢复开关均保留独立含义。

## 关键路径

现在：总览看到临期卡 → 找提醒设置确认是否自动用卡 → 再到通知记录理解结果。

提案：总览直接看到临期卡和状态 → 点开详情理解结果／下一步 → 只有改变规则时才进入已有设置。

## 验证目标与实施顺序

这些是待验证目标，不是已经取得的成效：

1. 先定义状态表和5个合成场景，确认文案、跳转与证据来源，再给一套具体原生画面供评审。
2. 五场景首次走查中至少4个能在10秒内回答“下一件事、是否自动、需不需要操作”；这是小样本设计检查，不推断整体用户转化率。不达标先改表达。
3. 原生双语／最小窗口画面通过后，再做共享模型、旧数据读取、记录关联及防重复回归；各入口对同账号、同一读数得出一致状态。
4. 当前单账号Mac做不消耗卡的实机路径，随后按既有脚本打预览包。真实兑换结果只在自然合格且用户授权的事件后观察，不为验收提前用卡。
5. 发布前执行逐项保留审计、隐私与包／远端检查；真实换号、多屏、Windows与真实兑换覆盖分别记录，继承0.3.0的限制须明确，不默认转为已通过。

成效观察采用走查答题、跨页次数、定位结果的操作次数、三入口矛盾数与升级数据保留结果。先记录0.3.0同任务基线再比较，不默认新增遥测、上传记录或云端指标。

## 保留与非目标

[65项旧能力](../0.3.0/FEATURE_RETENTION.zh-CN.md)继续默认保留，实施时对照[逐项审计](../0.3.0/RELEASE_AUDIT.zh-CN.md)登记触碰项、原入口和新等价入口，不能只凭测试总数宣称完整。保留账号历史、旧历史备份、权益／重置明细、Token页、Widget最近1小时图、所有桌面形态、关于、现有偏好与授权。字段、默认值、入口或授权范围发生实质变化须单独说明影响并取得同意；不要求用户回忆旧功能。

P1仅保留走查证实有必要的数据诊断跳转／说明微调。暂不纳入更多样式、更多提供方、跨设备云调度、新账号体系、遥测、精确工作时长或Windows功能对齐。Windows继续维护已有能力，不能用同步版号暗示拥有Mac新特性。Codex自动暂停／续接、Hook与全局notify实验不恢复。

开发与证据由实现方负责；产品评审把关范围和表达；用户评审具体新体验与明确取舍。已选视觉方向现以合成数据前端原型呈现，原生实现仍需后续独立验收；当前不需要选择新的技术路线。
